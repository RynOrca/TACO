# 待办：语音消息（含 Agent 语音回复）

状态：**未实现**，本文只做可行性评估与落地方案。结论是可行，成本可控。

## 一、DeepSeek 到底能不能做语音

能，而且不是"第三方套壳"，是官方接口。2026-11-13 DeepSeek 把自家 App 的能力通过 API 放出来了，其中包含独立的语音合成（TTS）和语音识别（ASR）。

官方 TTS（`api-docs.deepseek.com/guides/tts`）关键事实：

| 项 | 内容 |
| --- | --- |
| 接口 | `POST https://api.deepseek.com/v1/tools/tts`（整段文本）；`wss://api.deepseek.com/v1/tools/tts`（流式，边说边合成） |
| 请求体 | `text`（必填，≤10000 计费字符，body ≤64 KiB）、`voice_id`（`stella` 女声默认 / `tide` 男声）、`format`（`wav` 默认 / `pcm`）、`filter_markdown`（默认 true，自动去掉 Markdown 再念） |
| 返回 | 音频流；`wav` → `audio/wav`，`pcm` → 24 kHz 16bit 单声道裸流 |
| 语言 | 中/粤/英/日/韩/马来/阿/印尼/泰/越，**没有 language 参数，按文本自动判断** |
| 限制 | 单次最长 30 分钟音频；不支持变速、不支持断点续传；返回 429（并发>50）、503（繁忙）、504（超时）；正文会被内容审核，400 可能是 `Content Exists Risk` |
| 计费 | 每 1 万字符 $0.45（限时五折 $0.225）；中文一个字算 2 字符 |

`filter_markdown=true` 对我们特别省事：Agent 回复里的 `**加粗**`、列表符号不会被念出来。

ASR（语音转文字）也有独立接口，识别是"整段文件输入"，不是实时流。本次方案不需要它也能跑通。

## 二、两种语音消息，成本差很多

### A. 用户语音消息（说话 → 对方播放）

**不依赖任何第三方**，纯前端 + 现有附件通道：

1. `navigator.mediaDevices.getUserMedia({audio:true})` + `MediaRecorder` 录 `audio/webm;codecs=opus`
2. 录完把 Blob 走**已经存在的**附件上传接口 `POST /upload`（后缀白名单加上 `.webm/.ogg`）
3. 聊天消息 `msg_type='audio'`，与 `file` 完全同构，只是渲染成 `<audio controls>` 而不是文件卡片

工作量：前端约 150 行（录音状态机 + 波形/计时 + 上传），服务端只是白名单加两个后缀。

风险点：
- Chrome/Edge 录出来是 webm/opus，Safari 是 mp4/aac，跨浏览器要兼容（课程场景 Chrome 够用）
- 需要 HTTPS 或 `localhost` 才能拿到麦克风权限。我们的前端是 `http://127.0.0.1:8765`，属于 localhost，**可以直接用**；局域网其它机器走 http 会被浏览器拦，需要自签 HTTPS 或 `chrome://flags/#unsafely-treat-insecure-origin-as-secure`
- 移动端录完切后台可能丢流，课程演示不涉及

### B. Agent 语音回复（文字 → 朗读）

要接 TTS，链路：

```
Agent 返回文本 reply
   ↓ 服务端 POST /v1/tools/tts {text: reply(前 N 字), voice_id: stella, format: wav, filter_markdown: true}
   ↓ 收到 audio/wav，写入现有的附件目录 <32hex>.wav
   ↓ 消息里带 audio: "<文件名>"，与 file 消息同构
前端 <audio> 播放（或自动播放，需用户先有交互）
```

工作量：服务端约 40 行（一个 `tts.py` + 在 `_agent_task` 里按开关生成），前端约 30 行（<audio> 控件 + 开关）。

必须注意的点：

1. **别把整段总结都念出来**。Agent 回答可能上千字，按 10000 字符上限算每次约 $0.05，但体验很差。建议只念前 200-300 字，或者只念"待办/结论"那一段。
2. **做成开关**，默认关：右栏「Agent 语音播报」勾选后，之后每条 Agent 回复附带语音。原因：TTS 是**付费且不可缓存复用**的调用，群里每来一次总结都合成一次会烧钱。
3. **失败要降级**。TTS 挂了（429/503/504）就只发文字，并在卡片上标一句"语音合成失败"，不能因为语音把整个 Agent 回复吞掉。
4. **内容审核**：`400 Content Exists Risk` 是真实存在的返回，得当成正常失败路径处理。
5. **密钥**：TTS 用 `DEEPSEEK_API_KEY`，与现在聊天用的 `LLM_API_KEY`（可能是第三方兼容接口）分开配置，别混用。

## 三、还差什么才算"完整"

如果只做 A，语音消息能发能播，但**Agent 读不到语音内容**（历史里只有 `[语音]`），也没法"总结一下刚才那段语音说了什么"。想补齐就要接 ASR：

```
录完音频 → 上传附件 → 同时 POST ASR 拿转写文本 → 存进 messages.meta.transcript
                                    ↓
                       Agent 读历史时看到的是文字，能参与总结/待办
```

这一步是可选的，但答辩时"Agent 能把语音总结成待办"会明显更强。

## 四、建议的实施顺序

1. **用户语音消息**（无外部依赖，先跑通"能录能播"）
2. **Agent 语音播报**（接 DeepSeek TTS，加开关 + 失败降级 + 只念前 N 字）
3. **ASR 转写**（让 Agent 能理解语音，需要确认 ASR 接口细节与计费）

前两步加起来大约是一次会话的体量，第 3 步还要查 ASR 的具体端点与参数。

## 五、需要先确认的事

- [ ] 账号是否开通了 DeepSeek 的"应用 API"（TTS 属于这一类，只有 chat 权限可能返回 404）
- [ ] `voice_id` 只用 `stella` / `tide` 两个，演示时选一个固定下来
- [ ] 群里每条 Agent 回复都合成语音会不会太吵 → 建议默认只对 `@Agent` 的直接提问播报，定时总结不播
